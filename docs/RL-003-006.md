# RL-003…RL-006 — Reservation ledger, Cook Anyway, conflicts, plan integrity

## New files (Xcode synchronized folder — no pbxproj edits)

- **Stocked/ReservationEngine.swift** — pure `nonisolated` engine + immutable Sendable DTOs
  (`ReservationClaim`, `ReservationBreakdown`, `MealConflict`, `ProjectedShortage`,
  `ReservationShortageReason`, `ReservationPendingConsumption`, `ReservationSnapshot`).
  `compute(meals:inventory:pendingConsumption:now:)` walks meals chronologically
  (day → breakfast…snack), parses ingredient lines via the planner's
  `CookLaterCrossCheckEngine.parse` + `UnitMath`, matches inventory via `FoodNameMatcher`,
  consumes expiring-soonest first, excludes items that expire before a meal's date, and
  emits Total/Reserved/Available per item (Available floored at 0 — deficits become
  conflicts, never negatives). Unquantifiable matches reserve presence without inventing
  numbers or shortages. Deterministic (`now` injectable) and idempotent by construction.
- **Stocked/ReservationLedger.swift** — `@Observable @MainActor` singleton caching the
  snapshot keyed on `inventoryRevision × planRevision × overrideStamp`
  (`refreshIfNeeded(store:)` / `refresh(store:)`). Accessors: `breakdown(for:)`,
  `totalOwned/reserved/available(for:)`, `shortages()`, `conflicts()`,
  `reservedTouches(ingredientNames:)`. Also persists the Cook Anyway override log
  (`ReservationOverrideRecord`, LocalDatabase key `reservationOverrideLog_v1`, capped 100).
  An override's consumption projects forward only while `inventoryRevisionAtCreation`
  still matches — once inventory actually changes, physical data wins (no double count).
- **Stocked/ReservationOverrideSheet.swift** — RL-004 informative (non-blocking) review:
  reserved ingredients + amounts, affected meals + dates; actions Cook Anyway (records
  override, proceeds), Add Replacement to Grocery (`addToGroceryIfMissing`, deduped),
  Choose Another Meal. Item-backed payload (`ReservationOverridePayload`).
- **StockedTests/ReservationEngineTests.swift** — deterministic coverage: breakdown math,
  never-negative Available, chronological over-allocation (later meal flagged), conflict
  ordering, expiry-before-meal shortages, unquantified honesty, Cook Anyway consumption,
  loose reserved-name matching, cooked/building/served meals holding no reservations,
  and byte-for-byte idempotent recomputation.

## Caveats

- Planned-meal ingredient amounts are treated as already scaled to the meal (same
  assumption as CookLaterCrossCheckEngine); no recipe-base-servings ratio exists in
  `PlannedMeal` to scale against.
- Cook Anyway does not deduct inventory (reservations are derived, spec RL-003); its
  consumption is projected only until the next inventory mutation, then reality wins.
- Prepped/cooked-ahead meals keep their reservations (`prepared` flag on claims);
  `.served` releases them.
- No edits to GuestDataStore/CookingFlow/GroceryListView/HouseholdSync; store mutations
  go only through `plannedMeals` assignment (planner-owned) and `addToGroceryIfMissing`.
