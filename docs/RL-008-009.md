# RL-008 + RL-009 — Offline Sync Recovery & Social Recipe Import

## RL-008 — Offline Use and Synchronization Recovery

Verified first: HouseholdSync already persists its op queue (`DBKey.householdOpQueue` via
LocalDatabase) with per-op UUID + `createdAt`, LWW merge by `updatedAt`/`lastWriterID`,
durable tombstones, single-flight `syncNow`, and persisted exponential backoff. Dependents
recalculate via GuestDataStore didSets (`invalidateStockMatches` etc.) when a pull applies.
The gaps were: no reconnect trigger (offline edits waited for the 6 s poll or were lost for
one-shot posts), no relaunch-surviving queue for fire-and-forget Worker posts (activity
events), and no UI surface for pending work.

### New files
- **`Stocked/OfflineQueueCenter.swift`** — `@MainActor @Observable` façade:
  - `isOffline`, `pendingCount` (household ops + queued mutations), `lastSyncSuccess/Failure`.
  - Durable `OfflineWorkerMutation` queue (LocalDatabase key `offline_worker_mutation_queue_v1`,
    cap 200, 14-day max age, 12-retry poison guard). Each mutation carries a stable `opId`
    envelope; the payload keeps its original ids/timestamps → idempotent replay.
  - Reconnect flow: `connectivityChanged(online:)` fed by BOTH monitors; offline→online
    triggers ONE coalesced sync pass (single task, follow-ups collapse), min 10 s between
    attempts, exponential backoff (10 s → 5 min) on consecutive failures. Never tight-loops
    on flapping networks.
  - No success notifications by design — the badge disappearing is the signal.
- **`Stocked/OfflineQueueBadge.swift`** — `PendingSyncBadge`: OfflineBanner-style strip,
  "Pending N changes · will sync" / "…will sync when you're back online", plus a
  "having trouble syncing" hint when `hasStuckOperations`. Only shows when work is actually
  *waiting* (offline, stuck, or pending >15 s) so normal online edits don't flash it.
  Tap = manual coalesced sync nudge.

### Modified
- **`ConnectivityMonitor.swift`** — reports transitions to OfflineQueueCenter. (Note:
  `start()` was previously never called anywhere; the center's `activate()` now calls it,
  so `isOnlineFlag` finally reflects reality.)
- **`NetworkMonitor.swift`** — reports transitions; `OfflineBanner` now embeds
  `PendingSyncBadge`, so the badge appears everywhere the offline strip does (StockedShell
  already renders `OfflineBanner` — **no StockedShell edit needed**). Standalone hook for
  other screens: just add `PendingSyncBadge()`.
- **`HouseholdSync.swift`** —
  - `startAutoSync` activates the center (before the household guard, so solo devices get
    reconnect recovery too).
  - `noteConnectivityRestored()` clears persisted *transport* backoff on reconnect but
    keeps server-imposed pauses (429/quota) via new `backoffIsServerImposed` flag.
  - `reconnectSync()` — one recovery pass using the cached poll store.
  - `replayPost(_:_:)` — transport for queue replay.
  - `logActivity` now stamps each event with a stable `eventId` + original timestamp and,
    on failure, enqueues into the durable queue instead of dropping (was fire-and-forget).

## RL-009 — Social Recipe Link Import

### New files
- **`Stocked/SocialImportDetector.swift`** — platform detection (tiktok.com, vm/vt.tiktok.com,
  instagram.com, instagr.am, ig.me, youtube.com, youtu.be, youtube-nocookie, pinterest.* incl.
  country TLDs, pin.it), `normalizedKey` (strips www/m/mobile, fragments, tracking params;
  keeps YouTube `v`/`list`), and `existingImport(of:in:)` duplicate lookup that scans saved
  recipes' `notes` for a matching normalized source URL.
- **`Stocked/SocialImportFetcher.swift`** — 10 s-timeout fetch of PUBLIC og:title /
  og:description (caption) / og:image; entity decoding incl. numeric; private/deleted
  detection (401/403/404/410 + login-wall/tombstone markers) → typed `SocialImportError`
  with clear user messages; multi-recipe heuristic (≥2 "ingredients" headers or
  "Recipe 1/2:" markers). Never fabricates content.
- **`Stocked/SocialImportView.swift`** — `SocialImportSheet` preview-before-save:
  duplicate gate ("Already imported — Open My Recipes" / "Import Again Anyway"), verbatim
  extracted text structured through the SAME Worker `recipeImport` route
  (`RecipeImportAI.structure`, on-device `RecipeTextParser` fallback), preview of
  title/image/servings/ingredients/steps with **"Needs review"** chips on empty amounts,
  missing steps/servings, and a summary note stating nothing was guessed; multi-recipe
  note; Save (keeps `notes = "Saved from <Platform>: <url>"` — same convention as website
  saves, powers dedupe) or "Edit Before Saving" → CreateRecipeView prefill. Insufficient
  content → explanation + "Complete It Manually" or explicitly-labeled
  "Draft It with AI" (both via the existing CreateRecipeView prefill/AI-cleanup path).

### Modified
- **`SharedRecipeImporter.swift`** — share-extension URL branch detects social links first
  and uses og: metadata → prefilled form → existing CreateRecipeView AI structuring flow.
  Private/deleted posts surface a clear scrapeFailed message; caption text falls through to
  the shared-text parser when the fetch is thin. Source link is appended to `originalText`
  ("Source: …") so "Show original text" preserves it.
- **`WebRecipesView.swift`** — the existing "Import from URL" entry point routes social
  links to `SocialImportSheet` (new `WebSheet.socialImport` / `.socialForm` cases); sheet
  copy now mentions social platforms.

## Caveats
- Could not compile (no Swift toolchain in this environment); review was manual.
- `UserRecipe` has no dedicated `sourceURL` field (spec assumed one); the established
  convention (`notes` = "Saved from X: url", per WebRecipeDetailView) is used instead.
  On the share-extension path the link survives in `originalText` only, because
  CreateRecipeView (not in my ownership set) doesn't carry `AddRecipeForm.notes` through.
- Duplicate detection covers the paste path (WebRecipesView) fully; the share-extension
  path skips the dup gate (MainTabView's `Outcome` switch couldn't gain a case without
  editing an un-owned file).
- Activity-event idempotency relies on the Worker deduping by the new `eventId` (or
  tolerating duplicates in the capped feed); the worker is read-only for this change —
  flagged for the worker-owning agent.
- Starting `ConnectivityMonitor` (previously dormant) makes `isOnlineFlag` real; callers
  that guard on it (Worker client, receipt scan, etc.) now correctly short-circuit offline.
